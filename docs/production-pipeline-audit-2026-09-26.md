# Prompt-to-screen pipeline audit

This is a static audit of the local working tree on September 26, 2026. It includes the uncommitted planning fixes in this checkout. It is **not** a timing profile of production or a claim about another product's internals. The Drawgle production database was unavailable during this audit. "Earliest" means the earliest point at which the present inputs exist, not a promise that moving a call is risk-free.

There are three different things named "blueprint" in the code. `product_planning.blueprint` is the durable ledger of product facts. The functional roadmap is the saved screen/action/state graph. `planUiFlow` produces a build blueprint containing the project charter, navigation and batch roadmap before writing builder-grade screen briefs. Only the last two require a reviewable set of screen identities. Treating all three as one synchronous phase makes both the product and its progress display harder to understand.

## Actual critical paths and avoidable serialization

1. **First useful chat response:** the evidence assessment model completes before the early flow preview can be written. The same HTTP turn then enters the designer's potentially eight-round tool loop. Reference selection, fact review and readiness review may add model calls before the approval card. `runProductDesigner` also awaits the memory-task trigger before returning its final HTTP response. The preview is useful, but it is not proof the approval path is quick or reliable.
2. **Warm Build:** a matching scope preparation can reuse tokens, blueprint, briefs and assets. The coordinator still verifies approval/credits, starts a child, builds the first screen and checks it. A prepared plan is keyed to the exact visual and scope inputs. Cache-hit rate matters as much as task duration.
3. **Cold Build:** the worker can run reference analysis, creative direction, token generation/reconciliation, blueprint generation, brief generation/reconciliation, copy review and asset resolution before the first builder call. Progressive mode limits the first cold batch to one screen, but it does not eliminate these sequential dependencies.
4. **Duplicate speculative work:** `prepare-project-design` and `prepare-product-scope` can both generate project tokens when the latter starts before the former has saved its cache. A Build that starts while either is in flight can also take the cold path. Matching final cache keys prevent stale reuse, but do not by themselves prevent duplicate model work or a cold start.
5. **Visibility:** generation writes stage timings (`performanceV1`, including first stream chunk and first ready screen). The discovery route has trace hooks, but normal `app/api/agent/route.ts` calls do not pass `onTrace`, and there is no comparable persisted per-call timing for first prompt through approval. Static code alone cannot assign a percentage of the reported 71–119 seconds to each call.

## Production-grade target, preserving the lessons behind current safeguards

- **One canonical, versioned design request.** Store the original brief, corrections, explicit requirements, selected mode/reference and approved scope. The model may propose facts and a screen flow, but the server assigns stable identities, applies a single diff transaction, and checks revision/ownership. Keep legacy fact/roadmap readers while migrating existing projects; do not bulk-rewrite their histories.
- **One reviewable flow candidate per material revision.** Generate screen identities, visible tasks, actions and destinations as a typed candidate. Run deterministic graph checks immediately and one independent semantic coverage review before approval. A failed check returns exact issue IDs to a targeted repair, not a restart of reference selection, fact discovery and roadmap creation. Explicit user questions are reserved for consequential screen/flow choices.
- **A dependency graph of prepared artifacts, not one long chain.** Visual direction can start beside flow planning. Project tokens depend on stable visual input, not selected screen order. Scope blueprint/navigation depend on reviewed output IDs. A first screen brief depends on that blueprint; its assets depend on its brief. Each artifact records a versioned input hash, status, owner and expiry. Same-key work joins an in-flight task rather than running twice. Build can use each completed artifact without waiting for unrelated later-screen work.
- **One authoritative source per concept.** Keep product truth, selected output identities, project visual system, scope navigation and per-screen briefs distinct. Avoid maintaining conflicting copies of the same "blueprint" in model context, project JSON, roadmap metadata and run metadata without an explicit revision relationship.
- **Per-screen delivery with unchanged quality bar.** Build the first accepted screen, validate it at both mobile sizes, derive family rules, then admit parallel sibling builds. Keep navigation/asset/credit checks and user-visible progress. A failed screen remains retryable while accepted designs remain intact.
- **Measure before deleting a safeguard.** Persist anonymized spans for first prompt, assessment, each designer round, reference candidate inspection, flow review, approval card, preparation hit/miss, token/blueprint/brief work, first stream, viewport check and first ready screen. Record call counts, cache-hit reason and failure code without prompts or secrets. Compare paired outputs and actual user completion before merging review calls or removing a gate.

The first production change should be instrumentation and same-key preparation coordination, followed by reducing model/tool round trips in planning. The graph, approval/credits, reference integrity and rendered-screen checks are not candidates for blind removal. Target a useful first response within 15 seconds at p90 and a usable warm first screen within 60 seconds at p90, measured separately for prompt-only, curated, uploaded-style and exact-recreation modes. These are targets, not current measured results.
